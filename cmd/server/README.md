# Сервер

В директории `cmd/server/` находится точка входа Сервера. Она читает конфигурацию, создаёт `internal/server.Server` и запускает HTTP- и gRPC-транспорты.

Сервер принимает метрики по HTTP и gRPC, сохраняет их в выбранном хранилище и предоставляет HTTP API для чтения текущих значений.

Внутренняя архитектура и жизненный цикл Сервера описаны в [`internal/server`](../../internal/server/README.md).

## Поведение Сервера

Сервер одновременно слушает два адреса:

- HTTP-адрес для записи и чтения метрик
- gRPC-адрес для пакетной записи метрик

По итоговой конфигурации автоматически выбирается один из режимов хранения:

- PostgreSQL
- память с дополнительным сохранением в файл
- только память

Также Сервер может проверять доверенную подсеть и подпись HTTP-запросов, подписывать HTTP-ответы, расшифровывать входящие HTTP-запросы и отправлять события аудита.

## Конфигурация

Сервер поддерживает четыре источника конфигурации:

- значения по умолчанию
- JSON-файл
- флаги командной строки
- переменные окружения

Приоритет источников:

```text
env > flag > JSON > default
```

Путь к JSON-файлу задаётся флагом `-c`/`--config` или переменной окружения `CONFIG`. Для самого пути действует приоритет:

```text
CONFIG > -c/--config
```

## Параметры запуска

В каждой строке указаны флаг, переменная окружения, JSON-поле и назначение параметра:

- `-a` | `ADDRESS` | `address` - адрес HTTP-Сервера, по умолчанию `localhost:8080`
- `-g` | `GRPC_ADDRESS` | `grpc_address` - адрес gRPC-Сервера, по умолчанию `localhost:50051`
- `-i` | `STORE_INTERVAL` | `store_interval` - интервал файлового сохранения, по умолчанию `300` секунд
- `-f` | `FILE_STORAGE_PATH`/`STORE_FILE` | `store_file` - путь к файлу метрик, по умолчанию `metrics-db.json`
- `-r` | `RESTORE` | `restore` - восстанавливать метрики из файла при старте, по умолчанию `false`
- `-d` | `DATABASE_DSN` | `database_dsn` - строка подключения PostgreSQL; пустое значение отключает БД
- `-k` | `KEY` | `key` - ключ подписи HTTP-сообщений; пустое значение отключает подпись
- `--crypto-key` | `CRYPTO_KEY` | `crypto_key` - путь к приватному RSA-ключу для HTTP; пустое значение отключает расшифрование
- `-t` | `TRUSTED_SUBNET` | `trusted_subnet` - доверенная сеть в формате CIDR; пустое значение отключает проверку
- `--audit-file` | `AUDIT_FILE` | `audit_file` - путь к файлу аудита; пустое значение отключает запись в файл
- `--audit-url` | `AUDIT_URL` | `audit_url` - HTTP/HTTPS URL приёмника аудита; пустое значение отключает удалённый аудит
- `-c`/`--config` | `CONFIG` - путь к JSON-файлу конфигурации

Параметры `KEY` и `CRYPTO_KEY` относятся только к HTTP-транспорту.

## Путь к файловому хранилищу

Для пути к файлу поддерживаются две переменные окружения:

- `FILE_STORAGE_PATH` - историческое имя
- `STORE_FILE` - имя, соответствующее JSON-полю `store_file`

Если заданы обе переменные, `STORE_FILE` имеет более высокий приоритет.

## Валидация

После объединения всех источников проверяется итоговая конфигурация:

- адрес HTTP-Сервера не пустой
- адрес gRPC-Сервера не пустой
- интервал сохранения неотрицательный
- `TRUSTED_SUBNET` пустой или содержит корректную CIDR-подсеть
- `AUDIT_URL` пустой или содержит корректный HTTP/HTTPS URL с непустым хостом

## Конфигурация из JSON-файла

Пример находится в [`configs/server.example.json`](../../configs/server.example.json).

Значение `store_interval` задаётся строкой в формате `time.Duration` и должно содержать целое количество секунд, например `"300s"`.

```bash
./cmd/server/server --config=configs/server.example.json
```

## Запуск через Makefile

```bash
make run-server
make run-server-env
make run-server-config
make run-server-crypto
```

Примеры с прямым запуском бинарника ниже выполняются из корня репозитория после сборки Сервера.

## Режимы хранения метрик

Режим хранения выбирается автоматически по итоговой конфигурации.

### PostgreSQL

Если задан `DATABASE_DSN`, Сервер использует `PostgresStorage`. Файловые параметры в этом режиме не участвуют в хранении метрик.

```bash
./cmd/server/server \
  -a=localhost:8080 \
  -g=localhost:50051 \
  -d='postgres://metrics:password@localhost:5432/metricsdb?sslmode=disable'
```

После подключения к PostgreSQL Сервер автоматически применяет миграции из каталога [`migrations`](../../migrations/README.md).

### Память и файл

Если `DATABASE_DSN` пуст, Сервер использует `MemStorage`. При непустом пути `FILE_STORAGE_PATH`/`STORE_FILE` дополнительно подключается `FileStore`.

```bash
./cmd/server/server -f=metrics-db.json -i=300 -r=true
```

Значение интервала определяет режим сохранения:

- `STORE_INTERVAL > 0` - периодическое сохранение снимка
- `STORE_INTERVAL = 0` - синхронное сохранение после каждого изменения метрик

При штатном завершении выполняется финальное сохранение. Если включён `RESTORE`, состояние загружается из файла при старте.

### Только память

Путь к файлу по умолчанию равен `metrics-db.json`, поэтому для режима только в памяти его нужно явно очистить:

```bash
./cmd/server/server -f=""
```

В этом режиме данные теряются после завершения процесса.

## Доверенная подсеть

Если задан `TRUSTED_SUBNET`, Сервер проверяет IP-адрес Агента при выполнении операций записи метрик.

Для HTTP адрес читается из заголовка `X-Real-IP`. Запрос получает `403 Forbidden`, если заголовок отсутствует, содержит некорректный IP-адрес или адрес не входит в доверенную подсеть.

Для gRPC адрес читается из метаданных `x-real-ip`. Вызов получает статус `PermissionDenied`, если адрес отсутствует, некорректен или не входит в доверенную подсеть.

HTTP-маршруты чтения, главная страница и `/ping` проверкой не ограничиваются. При пустом `TRUSTED_SUBNET` проверка отключена.

Пример:

```bash
./cmd/server/server -t=192.168.1.0/24
```

## Подпись и шифрование HTTP

Если задан `KEY`, Сервер:

- проверяет заголовок `HashSHA256`, если он присутствует во входящем запросе
- возвращает `400 Bad Request`, если подпись запроса не совпадает
- добавляет `HashSHA256` в HTTP-ответы

Если задан `CRYPTO_KEY`, Сервер загружает приватный RSA-ключ и расшифровывает запросы с заголовком `Content-Encryption`.

Подпись и шифрование можно использовать независимо друг от друга. На gRPC-транспорт эти параметры не влияют.

## Аудит

Сервер может отправлять события об успешно обработанных метриках:

- в файл через `AUDIT_FILE`
- методом `POST` на удалённый URL через `AUDIT_URL`

Оба способа можно использовать одновременно. Если оба параметра пусты, аудит отключён.

Ошибки аудита записываются в лог, но не отменяют уже успешное сохранение метрик.

Формат события:

```json
{
  "ts": 12345678,
  "metrics": ["Alloc", "Frees"],
  "ip_address": "127.0.0.1"
}
```

Для HTTP-запросов поле `ip_address` заполняется из заголовка `X-Real-IP`, а при его отсутствии - из `RemoteAddr`. Для gRPC-запросов значение берётся из метаданных `x-real-ip`.

Каждое файловое событие записывается отдельной JSON-строкой. Удалённая отправка считается успешной при ответе со статусом `2xx`.

## Graceful shutdown

Сервер штатно завершает работу при получении:

- `SIGTERM`
- `SIGINT`
- `SIGQUIT`

После сигнала Сервер:

1. прекращает принимать новые HTTP-запросы и gRPC-вызовы
2. ожидает завершения активных HTTP-запросов и gRPC-вызовов
3. при превышении тайм-аута принудительно завершает оставшиеся соединения и вызовы
4. останавливает периодическое файловое сохранение
5. сохраняет финальный снимок метрик при файловом режиме
6. закрывает файл аудита и соединение с PostgreSQL

Для завершения каждого транспорта используется тайм-аут 30 секунд.
