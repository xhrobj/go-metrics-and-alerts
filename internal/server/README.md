# internal/server

Пакет содержит внутреннюю реализацию Сервера. Он создаёт зависимости, запускает HTTP- и gRPC-транспорты, выбирает хранилище метрик, настраивает файловое сохранение и аудит, а также управляет жизненным циклом принадлежащих Серверу ресурсов.

## Архитектура

```text
cmd/server
    │ создаёт
    ▼
server.Server
    ├── HTTP transport ─┐
    │                   ├──> MetricsService ──> MetricsStorage
    └── gRPC transport ─┘
              │
              └──> Auditor
                    ├── FileObserver
                    └── RemoteObserver
```

HTTP- и gRPC-транспорты используют один экземпляр `MetricsService`, общее хранилище метрик и общий диспетчер аудита.

## Структура

```text
internal/server/
├── server.go       # создание, запуск и завершение Сервера
├── grpc.go         # создание и завершение gRPC-Сервера
├── database.go     # подключение PostgreSQL, миграции и выбор хранилища
├── persistence.go  # восстановление и файловое сохранение метрик
├── audit_setup.go  # настройка диспетчера и получателей событий аудита
├── security.go     # загрузка приватного ключа и доверенной подсети
├── config/         # загрузка и валидация конфигурации
├── audit/          # события аудита и их получатели
├── migrations/     # запуск SQL-миграций
├── service/        # бизнес-логика работы с метриками
└── transport/
    ├── grpc/       # gRPC-сервис, преобразование сообщений и interceptors
    └── http/
        ├── handler/    # HTTP-обработчики
        ├── middleware/ # HTTP middleware
        └── router/     # маршруты и middleware-цепочка
```

## Инициализация Сервера

`server.New` выполняет последовательную сборку приложения:

1. загружает приватный RSA-ключ, если включено расшифрование HTTP-запросов
2. разбирает значение доверенной подсети
3. подключается к PostgreSQL и применяет миграции, если задан `DatabaseDSN`
4. создаёт `PostgresStorage` или `MemStorage`
5. создаёт общий `MetricsService`
6. настраивает диспетчер аудита и его получателей
7. создаёт HTTP- и gRPC-Серверы
8. открывает отдельные HTTP- и gRPC-listener'ы
9. настраивает восстановление и файловое сохранение для `MemStorage`

При ошибке инициализации уже созданные ресурсы освобождаются через `Server.Close`.

## HTTP-транспорт

HTTP-запрос проходит через роутер и цепочку middleware:

```text
HTTP-запрос
-> StripSlashes
-> логирование
-> проверка HashSHA256 и подпись ответа
-> расшифрование
-> gzip
-> проверка доверенной подсети для маршрутов записи
-> handler
-> MetricsService
-> MetricsStorage
```

Middleware проверки подписи и расшифрования подключаются только при наличии соответствующих настроек. Поддержка gzip подключается всегда, но распаковка запроса и сжатие ответа выполняются только при наличии нужных заголовков.

Проверка доверенной подсети применяется только к маршрутам записи метрик. Маршруты чтения, главная страница и `/ping` обходят эту проверку.

После успешного изменения метрик обработчик отправляет событие в общий диспетчер аудита.

Маршруты, форматы запросов и обязанности обработчиков описаны в [документации HTTP-обработчиков](transport/http/handler/README.md).

## gRPC-транспорт

gRPC-запрос проходит через цепочку unary interceptors к реализации сервиса `Metrics`:

```text
gRPC-запрос
-> LoggingInterceptor
-> TrustedSubnetInterceptor
-> Server.UpdateMetrics
-> преобразование protobuf в model.Metrics
-> MetricsService.UpdateMetrics
-> MetricsStorage
```

`TrustedSubnetInterceptor` извлекает IP-адрес Агента из метаданных `x-real-ip`. Если доверенная подсеть не настроена, проверка пропускается.

После успешного пакетного обновления gRPC-Сервер отправляет событие в тот же диспетчер аудита, который используется HTTP-транспортом.

## `MetricsService`

`MetricsService` содержит общую бизнес-логику работы с метриками и зависит от интерфейса `MetricsStorage`.

Сервис поддерживает:

- замену значения gauge
- накопление delta counter
- пакетное обновление метрик
- чтение gauge и counter
- получение снимка всех метрик

```text
HTTP handler ─┐
              ├──> MetricsService ──> MetricsStorage
gRPC service ─┘
```

Транспортные адаптеры зависят от интерфейса сервиса, а сервис не знает об HTTP-маршрутах, статусах, middleware, protobuf и gRPC-кодах.

В качестве `MetricsStorage` используются `MemStorage` или `PostgresStorage` из [`internal/repository`](../repository/README.md).

## Выбор хранилища

Если задан `DatabaseDSN`, Сервер:

1. открывает соединение с PostgreSQL через драйвер `pgx`
2. проверяет соединение с тайм-аутом 3 секунды
3. применяет SQL-миграции
4. создаёт `PostgresStorage`

При использовании PostgreSQL файловое сохранение не подключается.

Если `DatabaseDSN` пуст, создаётся `MemStorage`. В этом режиме может дополнительно использоваться `FileStore`.

Описание SQL-миграций находится в [`migrations/README.md`](../../migrations/README.md).

## Файловое сохранение

Файловое сохранение подключается только при одновременном выполнении условий:

```text
DatabaseDSN пуст
FileStoragePath непустой
```

Если включён `Restore`, при инициализации `FileStore` загружает сохранённые значения в `MemStorage`.

Дальнейшее поведение зависит от `StoreIntervalInSec`.

### Синхронное сохранение

При значении `0` метод `MetricsService.EnableSyncSave` подключает `FileStore` непосредственно к сервису. После каждой успешной операции изменения метрик сервис сохраняет новый снимок.

Синхронное сохранение применяется к:

- `UpdateGauge`
- `UpdateCounter`
- `UpdateMetrics`

### Периодическое сохранение

При положительном интервале запускается отдельная goroutine с ticker'ом. Она периодически сохраняет снимок `MemStorage`, не изменяя поведение `MetricsService`.

При завершении Сервера периодический цикл останавливается, после чего выполняется финальное сохранение. Финальный снимок также сохраняется при синхронном режиме.

## Аудит

Пакет `audit` реализует паттерн «Наблюдатель»:

```text
HTTP handler ─┐
              ├──> Auditor
gRPC service ─┘      ├──> FileObserver
                     └──> RemoteObserver
```

`Auditor` последовательно уведомляет всех подключённых получателей. Если один из них возвращает ошибку, остальные всё равно получают событие, а ошибки объединяются и записываются в лог транспортным слоем.

Событие создаётся только после успешного сохранения метрик. Ошибка аудита не откатывает уже выполненное обновление.

`FileObserver` записывает каждое событие отдельной JSON-строкой и синхронизирует конкурентную запись через mutex.

`RemoteObserver` отправляет событие POST-запросом с JSON-телом. Успешными считаются ответы со статусом `2xx`; HTTP-клиент использует тайм-аут 5 секунд.

Для HTTP-запросов IP-адрес берётся из заголовка `X-Real-IP`, а при его отсутствии - из `RemoteAddr`. Для gRPC-запросов адрес извлекается из метаданных `x-real-ip`.

Файл аудита закрывается при освобождении ресурсов Сервера.

## Жизненный цикл

`Server.Run` запускает HTTP- и gRPC-Серверы параллельно.

Завершение одного транспорта или отмена переданного контекста инициирует остановку второго транспорта.

HTTP-Сервер:

1. прекращает принимать новые соединения через `Shutdown`
2. ожидает завершения активных запросов
3. при ошибке или превышении тайм-аута принудительно закрывается через `Close`

gRPC-Сервер:

1. запускает `GracefulStop`
2. ожидает завершения активных RPC
3. при превышении тайм-аута вызывает принудительный `Stop`

Каждый транспорт использует тайм-аут завершения 30 секунд.

После остановки обоих транспортов `Server.Run` прекращает периодическое файловое сохранение и сохраняет финальный снимок. Ошибки транспортов и файлового сохранения объединяются и возвращаются вызывающему коду.

Отложенный вызов `Server.Close` в `cmd/server` освобождает оставшиеся ресурсы:

- останавливает файловое сохранение, если оно ещё не остановлено
- закрывает HTTP- и gRPC-listener'ы
- принудительно останавливает оставшиеся транспорты
- закрывает файл аудита
- закрывает соединение с PostgreSQL

Повторный вызов `Server.Close` безопасен.
